# Simulation tools

Headless tools of the Godot project. Their purpose (user, 2026-11-12): **try things out** to find out (1) whether the gameplay is fun and makes sense and (2) which prices skills will need. Skill prices are **not settled**; the runs ignore them, and nothing checks a monster against a budget or a cost. The runs give **indications only**: no balance validation, no price approval and no rule source.

Simulations run on the battle core itself (`battle/core`), on the same content files as the game.

## Tools and data

| File | Purpose |
|---|---|
| `sim.gd` | Bot-vs-bot runs; prints one run block (or one table row) in the format of [docs/simulation_log.md](../../docs/simulation_log.md). Default: random teams from the game's monsters; `--team-a` / `--team-b` field any monsters by id. |
| `compare.gd` | Side-swapped comparison of two monsters; prints a result table. |
| `progression.gd` | Side-swapped entry-proxy → single-stat upgrades → combinations; in-memory teamwide interventions, not approved progression or a price calculator. |
| `discovery.gd` | New skills, one-shot movement and map candidates using authored stats; reuses progression's measurement helpers, not its entry proxy. |
| `smoke_ui.gd` | Plays draft → placement → battle through the real UI (not a measurement tool). |
| `lib/sim_bots.gd` | Move policies `greedy` (AiBrain as the game plays it: it walks up to the enemy; `hunt` is the same bot), `wait` (AiBrain up to S011: ends the turn instead), `chase` (walks up only while not ahead), `plan` (AiBrain's evaluation over two actions of one turn, about five times slower), `tactic` (plans the whole turn and plays the best end positions on with greedy bots until the monster's next turn; about twenty times slower), `rush`, `kite`, `random`. |
| `lib/sim_runner.gd`, `lib/cli.gd` | Boards and start squares for fixed-team runs, the game loop, argument parsing. |
| `../data/monsters/*.tres` | One file per monster, including user experiments such as `asdf`; normal draws use the in-game status filter, not a fixed nine-monster list. Explicit tool teams may select simulation-only records. |

**Calculation costs:** there is no price folder or price calculator. `internal_calc_cost` in skill, zone, ground and prop Resources is an authoring note: older values come from the retired calculation schema; −1 means not calculated. It is not a current authoritative price, and no rule or tool uses it to check budgets; it is excluded from the content fingerprint. Prices belong to [Skills §5](../../docs/gdd_skills.md#5-value-and-prices), stat drafts to [Monsters §2.2](../../docs/gdd_monsters.md#22-frame-budget-level-ups). The progression/discovery tools include focused `--self-test` checks; those checks validate the harness and action fixtures, not gameplay balance.

## One data folder, one status scale

The project has one content folder, `data/`, with one folder per kind (user decisions 2026-11-12): `monsters`, `skills`, `zones`, `grounds`, `props`, `tamer`. The tools hold no data of their own, and there is no second skill, zone, kit, build or price set: a monster is one file (`data/monsters/<id>.tres`) with its species data, stats and kit, whether the game or only a simulation uses it.

Skills (`BattleSkillDef`), monsters (`MonsterDef`), grounds, zones and props (since 2026-11-13) carry `content_status` (`battle/defs/content_status.gd`):

| Value | Meaning | Used by the game |
|---|---|---|
| `approved` | released content (none exists yet) | yes |
| `draft` | GDD draft or test content the game currently plays with (the default) | yes |
| `experiment` | a mechanic the user wants to try in the game (since 2026-11-13; e.g. rare, expensive skills that change AP or turns per round); labelled in the overview | yes |
| `test` | exists only for automated tests | never |
| `simulation` | exists only for simulation runs (monsters, skills, grounds, zones or props) | never |
| `archived` | kept for reference but no longer used; not in the default lists of the tools either | never |

`ContentStatus.in_game` is the shared status predicate used by both registries. These labels control availability, not gameplay/rule approval: `GameData.monster_ids()` (draft screen, enemy teams, overworld) and `BattleContent.game_monster_ids()` return only game monsters; a monster of the game may not hold a test-only or simulation-only skill (content check); the content fingerprint covers only what the game can field.

**A new test monster** is a new file in `data/monsters` with `content_status = "simulation"`: any stats, any one to four skills. Nothing checks its stat points or costs. The sixteen former test builds and their eleven reference skills were deleted on 2026-11-12 (they were built to compare prices of the timed Surge); retire something you want to keep by setting `archived` instead.

## Commands

**Since the reshape of 2026-11-13** the game has no Surges, traps, Mountains or flyers ([gdd_battle §1.2](../../docs/gdd_battle.md#12-battle-design-pillars)). The variants below that act on them (`alltraps`, `alltimed`, `turns=N`, `trapcap`, `trapfade`, `castersurge`, `fairsurge`, `unfairsurge`, `surgewall`, `surgeground`, `surgedmg`, `noshield`, `shield=N`, `shieldap`, `--shield-once`) still parse but change nothing in a run on the game's content; they go with the code clean-up (temp_todo I57). The variants to work with now: `mixstats`, `mixskills`, `mixkits`, `genskills=N`, `calm=N`, `veinhold`, `wells=N`, `noflank`, `delay`, `delay=reverse`, `delay=first`, `startback`, `stat=…`, `swap=old>new`, `freeap=N`, `freemod=N`, `strikedmg=N`, `groundfade=N`, `tpr1`.

Run from the repository root; everything after `--` belongs to the tool. Replace `<state>` with a literal code-state label (include dirty-tree context); a content fingerprint alone does not identify all source changes.

**Normal game versus measurement:** the normal 7×7 setup has three Dragon Veins and current in-game ZONE PUSH/PULL skills cost 1 AP, including mixed-effect Bog. `sim.gd --variant currentap=2` and `--current-ap 2` in the other harnesses test an unadopted cost candidate, not monster AP. Discovery's `single_vein` is also unadopted; no normal defaults follow from a measurement.

| CLI | Current interface / defaults |
|---|---|
| `sim.gd` | `--help`; positional defaults `20 3v3 1`, state `not given`; both bots `greedy`. `--paired` matches starts across runs but does **not** swap sides. |
| `compare.gd` | `--help`, `--monsters a,b`, `--seeds` (1,2,3), `--pairs-per-seed` (10), `--sizes` (5,7; accepts 5,6,7,9), `--bot` (`greedy`), `--board flat|layout` (`flat`). |
| `progression.gd` | `--help`, `--self-test`, `--seeds` (401,402), `--pairs` (4), `--bot` (`greedy`), `--current-ap 1|2` (1), `--scenarios` (see `--help`). No positional arguments. |
| `discovery.gd` | Same named options as progression; seeds 501,502, pairs 4, bot `greedy`, `--current-ap` **2** by default, authored sheets rather than entry proxy; `--help` lists default and optional scenarios. |

There is no CLI `--status` filter: normal pools use `ContentStatus.in_game`; explicit test-team selection and discovery's local substitutions do not release content to the game. `--self-test` and `--help` are separate execution modes, not measurement scenarios.

```sh
godot --headless --path godot -s res://tools/sim.gd -- 20 3v3 1 "<state>"
godot --headless --path godot -s res://tools/sim.gd -- 40 3v3 1 "<state>" --paired --compact-head --bot-a plan --bot-b plan
godot --headless --path godot -s res://tools/sim.gd -- 20 1v1 1 "<state>" --team-a blaze_tiger --team-b forge_golem --bot-a rush --bot-b rush
godot --headless --path godot -s res://tools/sim.gd -- 50 3v3 1 "<state>" --team-a blaze_tiger,forge_golem,gloom_wolf --experiment props
godot --headless --path godot -s res://tools/sim.gd -- 1 1v1 1 --team-a blaze_tiger --team-b moss_turtle --trace

godot --headless --path godot -s res://tools/compare.gd -- --seeds 1,2,3 --pairs-per-seed 10 --sizes 5,7 --bot rush
godot --headless --path godot -s res://tools/compare.gd -- --monsters forge_golem,moss_turtle --bot rush
```

- **`sim.gd` arguments:** `[battles] [mode] [seed] [state] [kits]`, then options. `--team-a` / `--team-b` field monsters by id (`--team-b` defaults to `--team-a`); `--bot-a` / `--bot-b` pick the policies; `--board` is `seeded` or `layout` for random-team runs and `flat` (default), `layout` or `seeded` for fixed teams; `--props a,b` adds one mirrored pair per prop id to a fixed-team run; `--experiment props` (with `--pairs N`) and `--experiment bots` print one block per row; `--trace` prints the board before every turn of one battle.
- **Further options of `sim.gd`:** `--variant a,b` sets the open test switches of `battle/core/battle_experiment.gd` for the run: `push=2` / `push=slide` (Strike and Surge pushes and pulls move further) and `kinpush` (Beast Strikes push, a Spirit Strike trades squares). `--shield-once` makes every shield zone skill once per round for the run, `--pressure N` shifts the start of late-round pressure, `--paired` gives battle *i* the same teams and board in every run, `--compact` / `--compact-head` print one table row per run. `--variant softpressure=N` replaces late-round pressure by one without damage (every N rounds the outer ring of the board breaks away, down to 3×3), `noshield` makes shield zone skills unusable, `jab=1` sets the Jab to 1 AP. The last compact column counts the battles that reached pressure by whether the side leading by total HP at that moment won, lost, had no lead, or the battle had no winner. The row ends with five usage columns: activations per battle by skill kind (Step separately), kit slots of each kind fielded per battle, activations per fielded slot, the most used skill with its share, and fielded skills never used; they show whether a kind is used much only because the kits hold many slots of it. Three more columns follow (since S010): the share of battles under 3, over 7 and over 10 rounds with the longest battle, the mean round of the first defeat, and monsters defeated before their own first turn per battle. Board-edge damage and spiky props are active build behaviour; trap Surges are legacy/test-only, not active rules; the variants measured before that (timer, edge damage of Surges, grown footprint, caster line, held Surges) were removed from the code and are documented in entries S002–S004 of the simulation log. Background: T38 in [temp_todo.md](../../docs/temp_todo.md).
- **Dragon Vein defaults** (legacy CLI/event names still use `wells` / `well`): `wells=3` on normal 7×7, ownership by last touch, surrounding on, TPR from round 2, late-round pressure only when no vein is owned. Compare using `--variant wells=N` (0 = none), `noflank`, `tpr1`, `latepressure=always` / `none`, or `delay` (postpone once per round). Vein/surrounding diagnostics report damage and defeats; they are not objective-quality scores. Discovery's `single_vein` is the matched count control; changing generator `wells=N` can also change prop placement.
- **Switches and options added for S011/S012:** `--variant groundfade=N` (ground laid during the battle turns back into Plain at the end of the N-th round; **build rule 2**, 0 = never), `trapcap=N` (at most N traps per trap skill and monster; one more removes the oldest; legacy/test-only setting 1, 0 = no limit), `trapfade=N` (an unsprung trap lapses at the end of the N-th round; not a rule), `stat=monster.field:value` (one stat of one monster for this run, e.g. `stat=forge_golem.move:2`), `noshield` (now the battle switch `no_shield_zones`), `shield=N` (Surge reduction of shield zones), `startback` (all monsters start on the back row), and content changes for one run only: `swap=old>new` (every kit holding skill `old` holds `new`), `hp=±N`, `hpmin=N`, `hpmax=N`, `tprmax=N`, `apmin=N`, `surgedmg=±N`, `strikedmg=0–4`, `zoneonce` / `castonce` (zone skills, or all placed skills, once per round). `--no-kind-a` / `--no-kind-b <kind>` makes the bot of one side never use a skill kind (strike, surge, trap, zone, ground, move), to measure what the kind is worth to the side that keeps it. With the environment variable `SIM_DEBUG` set, a full-block run prints every defeat with its round and cause and the winner of each battle. A variant row names its bots unless both sides play `greedy`.
- **Movement skills:** `--variant freeap=N` sets the AP of every movement skill other than Run (reference skills: 2; user experiments may differ), `freemod=N` takes N squares off their Movement (authored: 0).
- **Switches of S017 (2026-11-13; all off by default):** `--variant delay=reverse` (monsters that postponed act in reverse order), `delay=first` (postponing only in round 1, for monsters with two turns and the first of the queue), `calm=N` (no damage in the first N rounds), `surgewall` (no movement enters the squares of a charging timed Surge), `surgeground[=id]` (a timed Surge without ground of its own leaves this ground, default Thornbed). **Random draws for a run:** `mixkits` (every monster plays a random kit from the current in-game pool), `mixskills` (four random skills out of every skill of the game, the first one a Strike with damage), `mixstats` (HP 3–8, initiative 1–9, Movement 1–5, Reach 2–4, TPR 1–2, AP 2–3, each drawn alone). With them the block ends with a table of win rates per drawn kit, body + kit pair, skill and stat value.
- **Reshape of 2026-11-13:** `--variant genskills=N` makes `mixskills` draw from N generated skills (`battle/defs/skill_gen.gd`, class `SkillGen`: random legal skill sentences, kept in memory only; the same class serves the in-game skill builder); the block then lists win rates per part (`part:kind=…`, `part:shape=…`, `part:stays=…`, `part:ap=…`). `mixskills` alone draws from every skill of the game. `veinhold` and `unfairsurge` switch back to the rules before the reshape (a Dragon Vein only works while held; a due Surge does not wait). `mixkits` draws from the status-filtered in-game pool, including user content such as `asdf`; the former `kit_*` files are not a second active kit set.
- **New Resource classes or scripts:** run `godot --headless --path godot --import` once (or open the editor) so the class cache knows them.
- **A script that fails to compile does not quit by itself:** add `--quit-after 3` (or a `timeout`) to unattended runs.

## CPU use and optional low-load launcher

**Full CPU use is allowed (user authorization 2026-11-14).** The former low-CPU execution policy is not mandatory. Run Godot directly using the commands above with normal process/CPU settings; no code change is required. This permits available CPU use, not automatic parallelization or a promise that every run saturates all CPUs. Choose separate processes deliberately when appropriate; retain separate commands, seeds and outputs.

**Optional Windows low-load launcher:** run `godot/tools/run_low_priority.ps1` from the repository root with `-Godot` (console executable), `-Output` (stdout path), and `-SimArgs` (PowerShell string array of simulation arguments). It runs one Godot process at Idle priority on logical CPUs 2 and 3 (affinity `0xC`; intended for the current 32-thread machine), with single-threaded scene processing. `-TimeoutSeconds` defaults to 600 and kills an overrun; script errors fail the launcher. `-Import` runs the bounded editor import instead of the simulation; `-Script` selects another tool, such as `res://tools/progression.gd` or `res://tools/discovery.gd` (default: `sim.gd`). `-RawScriptArgs` omits the `--` separator for runners such as gdUnit4 that parse Godot's main command-line arguments. Stderr goes to `<Output>.stderr`. This intentionally throttled mode remains useful while gaming, but is not required. It limits CPU availability, not memory or total system latency; it is not the full-CPU invocation.

## Full-output measurements

For current 3v3 runs, the **mean-round target is 3–5**; outliers remain **<2 or >5 rounds**. Full output adds an exact round-count histogram (count and percentage for each observed integer) and every outlier, with its 1-based battle index, seed, RNG state before setup, both teams, winner/result and rounds. Draws and 600-turn timeouts are included; a timeout's rounds are its observed stopping point, not a completed battle duration. Paired runs show the derived per-battle seed; unpaired runs share the run seed and advance one RNG stream, so the seed alone does not independently reproduce an individual battle. Keep the command/content state and battle index; the RNG state is additional diagnostic context.

The full skill table lists **all fielded skills**, including zero-use skills and passives, sorted by uses descending (ties by id): total uses, total fielded kit slots across all battles and uses/slot. This normalizes kit availability, not survival time, turns or AP opportunities; passive zeroes do not mean their effects never applied. Step is reported separately, without a kit-slot denominator. Source inspection of `Battle._use_skill`, `BattleMoves.execute` and `BattlePayload._phase_damage` shows mutually exclusive activation events (`strike`, `moved`, `cast`, `surge_declared`), not Strike+Move+Cast duplicates. Movement display names are resolved to skill ids through the actor's kit; these are activation counts, not hit or damage counts. Compact output keeps its existing columns. Stats remain available through the optional `kits` roster listing and the `mixstats` result table (exact appearances, wins and percentage); this adds no stat-effect or balance validation. Full damage output includes `well` (Dragon Veins) and `flank` (surrounding); older raw blocks without these columns still include their damage in the total.

## Targeted displacement experiments

These options alter only the running simulation, not the Resource files or the game's defaults. Use `--paired` with the same seeds and battle counts for matched starting teams/boards; this is not a side-swapped trial.

| Variant | What changes | Question isolated |
|---|---|---|
| `currentap=N` | All in-game skills of kind `ZONE` carrying PUSH/PULL cost the positive integer N AP | Is repeatable area displacement too efficient per AP? |
| `currentonce` | The same skill family becomes once per round | How much comes from repeated use of one slot? |
| `openmap` | Remove preplaced props without aftermath after setup; no extra RNG draws, starts and Dragon Veins preserved; skills can still create props | How much does the starting prop geometry contribute? |
| `lifethread` | Every fielded unit receives the existing once-only survival at 1 HP | Could a one-shot protection help? This is a stress test, not an item/loadout implementation. |

Full output also lists damage sums and positive instances by raw kind/source, repeated actor + skill activations within one turn, and exact before-first-turn defeat counts plus affected battles. Source labels are existing events, not a reconstructed skill attribution; `Collision` does not distinguish monster versus prop blockers. Repetition uses skill IDs because activation events do not carry slots. Later zone ticks are not activations. `--trace` adds the round-labelled event timeline after the battle. These measurements describe bot behaviour, not fun, fairness or stat prices; in particular, having acted once does not prove a later burst offered a response window.

## Entry and upgrade comparisons

```sh
godot --headless --path godot -s res://tools/progression.gd -- --self-test
godot --headless --path godot -s res://tools/progression.gd -- --seeds 401,402 --pairs 4 --current-ap 2
godot --headless --path godot -s res://tools/progression.gd -- --seeds 401,402 --pairs 4 --current-ap 2 --scenarios both_hp,both_ap,both_tpr,both_strike_ground,both_hp_ap,both_hp_tpr,both_hp_ap_tpr,both_hp_ap_tpr_ground
```

- **Entry proxy, not an approved start:** AP 2, TPR 1, otherwise authored stats and kits. This does not construct a legal stage/frame/budget or assume the prototype's monsters are starters. `--current-ap 1|2` selects bilateral PUSH/PULL ZONE costs, including mixed-effect zones such as Bog: 1 is the current normal cost and progression's default, 2 is a working candidate, not adopted. No Resource is saved or source price changed.
- **Matched and side-swapped:** each seed draws two disjoint in-game teams of three and one setup seed per pair. Every scenario plays fresh sheets on that setup twice, swapping the entire teams. A unilateral scenario upgrades every subject-team member; `both_*` upgrades both teams and tests escalation, not unilateral value. Different scenarios and side swaps are correlated observations, not independent evidence or equal-cost builds.
- **Interventions:** `base`; `hp`, `initiative`, `movement`, `reach`, `ap`, `tpr` (+1 subject to printed caps); `strike_ground` (append existing Thornbed to damaging Strikes without a ground operation, with unchanged AP/damage); combinations `hp_ap`, `hp_tpr`, `ap_tpr`, `ap_tpr_ground`. `both_*` scenarios include the bilateral combinations shown above and `both_ap_tpr` / `both_ap_tpr_ground`. Slot development never lowers AP. The skill addition is proposed test content, not an approved upgrade choice.
- **Output:** exact wins/losses/Draws/timeouts, mean and round histogram, <2/>5 counts, pre-first-turn defeats, turns to first defeat, collision/total damage, repeat activations, actual applied deltas/cap blocks, skill uses and starting slot affordability. Affordability is AP-only, not target legality or proof of a viable kit; activation counts pool both teams. Unlike `sim.gd`, this report has aggregate histograms, not an individual outlier replay list. Scores count true Draws as 0.5 and exclude timeouts.
- **Isolation and provenance:** skill trees use `duplicate_deep(DEEP_DUPLICATE_ALL)` so external zone resources are isolated too. Self-tests check copies, caps, interventions and unchanged sources. A measurement checks the source content fingerprint again and prints `PROGRESSION_MEASUREMENT_COMPLETED` only on success. The printed harness SHA identifies this script only, not all engine dependencies; retain the repository state, command and content fingerprint. Completed blocks go unchanged into the simulation log, with conclusions/open work under T02/T03/T05/T13.

## Authored gameplay discovery

```sh
godot --headless --path godot -s res://tools/discovery.gd -- --self-test
godot --headless --path godot -s res://tools/discovery.gd -- --seeds 501,502 --pairs 4 --current-ap 2
godot --headless --path godot -s res://tools/discovery.gd -- --seeds 501,502,503,504 --pairs 4 --current-ap 2 --scenarios mist_step,mist_control,split_mist,split_mist_control
```

- **Authored sheets, no entry proxy:** stats, AP and TPR stay as authored; full HP, canonical team draws and complete side swaps. `--current-ap 1|2` explicitly selects the bilateral PUSH/PULL ZONE cost candidate; default 2 is a measurement choice, not a change to the game. Candidate substitutions affect subject A, except `both_*`; map changes affect both teams. Substitution is an opportunity cost, not a free extra skill or an equal-price comparison.
- **One canonical definition:** the four simulation-only skills `mist_step`, `receding_blow`, `cloudstep_token`, `raise_reed_screen` and prop `reed_screen` live in `data/`. Their effects are defined in those Resources, not a second tool catalogue. They are excluded from the normal game, builders' in-game choices and the overview's **In game only** view. The debug overview checkbox starts off, so its unfiltered view can display these non-game records; this is not game availability. Cloudstep occupies a kit slot: this is not a slot-free item implementation. The original kits and user experiments remain unchanged.
- **Slot substitutions:** Mist/Cloudstep replace the first movement skill; Receding Blow the first damaging Jab without board operations (Winged already retreats); Screen the first prop-only placement, else first ground skill, else final slot. Reports include eligible/unchanged units and exact species/old→new ledgers. `mist_control` and `split_mist_control` clear only the local Mist Step copy's board operations, preserving its 2-AP walking profile; the reported ID remains `mist_step`, marked `[no trail]` in the ledger.
- **Map candidates:** `open` removes starting props without aftermath. `screens` lays exactly two point-mirrored fragile screen pairs, excluding starts, veins and cardinal vein neighbours, preferring separated props. `split` moves the three veins to `(1,2), (3,3), (5,4)` and uses the screen generator. Changed legal prop positions mean this is not a pure vein-placement ablation. Placement uses its own setup-seeded RNG, without advancing play RNG. Screens block movement, not ranged targeting. `split_mist` / `split_cloud` combine map and subject skill; `both_mist` / `both_cloud` / `both_screen` substitute both teams.
- **Vein-count control:** `--scenarios base,single_vein` compares three veins with one central vein. Both start from the same generated board; `single_vein` changes only the outer two vein cells to Plain before battle, retaining all props, occupants, stats and RNG state. This isolates the count intervention rather than also changing prop generation. The game default remains three. Run with `--current-ap 1` for the present current-skill costs and `2` for the working cost candidate; neither sets monster AP.
- **Interpretation:** inherited map-only rows say `unilateral`, but maps are bilateral; their A score measures team outcomes under that map, not map quality. Diagnostics include candidate uses/slots, activation rounds, usage per battle, map hashes and well/flank damage. “No-own-turn” counts defeats after first positive damage without a subsequent own turn; it is descriptive, not a fairness verdict. A frequently used carrier does not establish the value of its attached zone: use the no-trail control.
- **Validation/provenance:** self-tests cover loaded Resources, clone isolation, map invariants and deterministic real-action fixtures. Source/candidate guards and a completion sentinel reject mutated/incomplete measurements. Own/parent script hashes and candidate file hashes complement the regular fingerprint, which excludes simulation content; keep the base commit and core changes with each report. Store completed reports unchanged in `docs/simulation_log.md`; correlate duplicates rather than counting reruns as new evidence.

## What a run covers

- **Active content resolved by the battle core:** Strikes, movement, grounds, zones, props, extra turns (TPR), board-edge legality/damage, Dragon Veins, surrounding, late-round pressure and Draws. Surges/traps, Mountains/height and flyers/air remain dead game paths exercised only by legacy/custom test fixtures, not active content or normal-run coverage.
- **Board of a fixed-team run:** `flat` is an empty board of the mode's size without Mountains; start squares are drawn by the seed from side 0's start area ([Battle §4.1](../../docs/gdd_battle.md#41-battlefield-generation)) and mirrored for side 1. On 1v1 the start area is the corner square, so seeds differ only through the bots' tie-breaks.
- **Not covered:** tamer skills, 2×2 and air units (no monster fields them), human play.

## Bots

`greedy` is `AiBrain`, the game's own opponent: one-step lookahead on a copy of the battle; since the user decision after S011 it also walks toward the nearest enemy (walking distance) when it has AP left and no better action, unless the position gets worse by more than about one point of hazard damage (`hunt` names the same bot, as in the S011 tables). `wait` is the AI as it was before: it ends the turn instead. `careful` is `greedy` with the switch `ai_careful`: it counts the Strike damage enemies can bring to each of its monsters within a round and avoids squares where that is lethal (S014: it loses to `greedy`, 43–45 %). `tactic` (since 2026-11-13) searches every order of actions the AP allow (a beam over `AiBrain`'s evaluation, kept in a plain and a threat-aware ranking), then plays the best few end positions and, with `--variant delay`, the postponed turn on with `greedy` for both sides until its monster is up again, and takes the line with the best position at that point. `plan` evaluates two actions within the current turn. `tactic` can consider a Strike followed by a step back and the double turn across a round border; it still assumes that everyone else plays `greedy`. `chase` walks up only while its side is not ahead in total HP (the side that would win by waiting for late-round pressure waits). In S010/S011 `hunt` lost to the waiting `greedy` under the build rules (40–44 %) and beat `rush` clearly. `rush` strikes whoever stands in a shape, otherwise casts, otherwise walks toward the nearest enemy; `kite` backs away when an enemy is within 2 squares; `random` picks a random legal action. All of them only take actions the battle reports as legal. `plan` searches two actions and `tactic` plans a whole turn with a bounded greedy continuation; neither is an optimal opponent. The simpler policies lack that planning. No policy provides dedicated prop-targeting, purposeful timed-effect refresh or tamer-skill play, so stalling and late-round pressure can decide a run. `rush` and `kite` rank movement by walking distance; `AiBrain` uses board distance and can stand still on an exact diagonal with Movement 1 (tracked as I42 in [temp_todo.md](../../docs/temp_todo.md)).

Rough speed on one core: `rush` about 40 ms per 1v1 battle; `greedy` about 0.1–0.3 s per 1v1 battle and 1–2 s per 3v3 battle; `tactic` about 20–25 s per 3v3 battle (hardware/content dependent; separate processes per seed are optional, not automatic).

## Validation boundaries

The goal is playable monsters from the start and meaningful alternative upgrades, not a predetermined AP/TPR start. AP affordability, one affordable active skill, budget fit and an entry proxy do not prove viability. ## Reading comparisons

`compare.gd` plays every seed **twice with swapped sides** on the same mirrored start squares with the same bot and no tamer skills. A Draw, including a timeout after 600 turns, scores 0.5. The table reports the stat points of both sheets (information only), wins, Draws, mean score, mean rounds and timeouts; SD and range describe the **seed-block mean scores** of monster A, not confidence intervals.

Two monsters that differ in more than one thing probe the whole sheet, **not the value of a single skill**; change one thing at a time to learn about it. High Draw rates or bot stalling make a 50/50 score meaningless. No price, budget or rule change follows from a run by itself.
